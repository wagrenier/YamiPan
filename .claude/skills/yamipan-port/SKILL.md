# YamiPan: the next PS2 decomp + PC port

YamiPan reconstructs a PS2 game function by function into C++ that runs on a PC platform layer. It is
the fourth port by the same author: MioPan (Fatal Frame 2, `../MioPan`), ReiPan (Fatal Frame 3,
`../ReiPan`, ported from FF2's symbolised debug build) and RosePan (Rule of Rose, `../RosePan`, no
counterpart: every function from its own binary). This skill distils what those three learnt; their
skills keep the full history. It is the playbook and the project's memory: follow it, and keep it true
("Keeping this skill alive").

**State (2026-10-30): before bootstrap.** The game is not named yet (open-items.md "Next up" 1). What
exists: multi-instance Ghidra (`tools/reverse/ghidra_mcp.py`, `ghidra_bridge.py`, `.mcp.json`). Until
the TU loop runs, work follows `references/bootstrap.md`; afterwards, the protocol below.

Read before working:
- `references/open-items.md` -- the user's priorities ("Next up"), decisions, questions.
- `references/status.md` once it exists (generated by `status.py`): TU summary, frontier.
- As needed: `ghidra.md` (instances, GhidraMCP traps), `bootstrap.md` (a new port, step by step),
  `architecture.md` (what the game is made of), `reconstruction.md` (how code is written, both GCC
  ABIs), `hazards.md` (traps from FF3 and RoR). PS2 / GS / VU / renderer knowledge lives in MioPan's
  skill (`../MioPan/.claude/skills/miopan-reversing/SKILL.md`: "Renderer architecture", "Diagnosing it
  does not render", "VU0 macro-mode idioms"): read the section, don't copy it.

## Bootstrap (until the loop runs)

`references/bootstrap.md`, in order, each step checkable: the game identified -> its own Ghidra project
-> RosePan's tools carried over on `ghidra_mcp.py` -> names seeded (ELF symbols, libraries, vtables,
folded functions, a sister game if any) -> the TU map -> the platform layer (host task) -> a green build
whose run shows a window and reached stubs -> the queue. Record each step's facts in architecture.md and
tick it in open-items.md. Decisions that shape the tree (layout, platform changes) are the user's: ask,
and when no answer can come, decide, record it in open-items.md "Decisions", and go on.

## One TU per session (the protocol)

Work is cut into translation units: one game object file, rebuilt as one source file under `src/` (key
= its path). Each session takes one TU (or a slice of a big one) from claim to commit; nothing carries
over in the conversation, everything in the repo (`tools/reverse/data/tus.json`, this skill, git).
Invocations: `/yamipan-port tu <TU>`, `/yamipan-port next`; any other request is regular work that
still ends in a commit.

1. **Claim and read.** `python tus.py claim <TU>` (or `next --claim`), `python tus.py brief <TU>`,
   read `work/tu/<slug>/brief.md` (handoff notes first) and the staged bundle (decompilation, class
   role, callers, callees, strings). The brief's **slice** is the session's work (reached stubs, then
   frontier, then their same-TU callees; ~10 KB of code). A **host task** (no game functions, queued with
   `tus.py queue <key> --top --task TEXT`) skips 2-5.
2. **Boundaries.** An extent is inferred until pinned; source-path strings are facts, link-order fill
   and class majority are guesses. Settle it from the brief's identity section, pin it with
   `tus.py define <file> <lo>-<hi> [...] --why "..."` (hi exclusive; list every range), give an
   `unassigned@` run a real file in the game's layout. Naming the file must not stall the work.
3. **Names.** Every slice function and direct callee you need gets a real name: `ctxcard.py` for
   evidence, a batch JSON in `work/batches/` (highest number + 1), `name_ctx.py <batch>` (tag + one-line
   `why`; it saves and refreshes). Members are `Class::method` (slot class from `rtti.py`, a non-virtual
   member's from its callers passing the object in a0). Re-brief when names changed.
4. **Header first.** `src/<dir>/<file>.h`: classes and structs at the EE offsets with `static_assert`s
   (or `layout: host` with the EE offsets in comments), globals, prototypes of what other TUs call, each
   member with `// <TAG> 0x...`. Outgoing calls get prototypes in *their* TU's header so stubgen can stub
   them. No `ptr + 0x120` in finished code.
5. **Code.** Reconstruct the slice (reconstruction.md): the game's semantics, `<TAG> 0x<addr>` above
   every function, methods as members in vtable order, asserts as the project's macro with their text,
   draws through the host draw module. Delete this TU's stubs in other files. Context still light: next
   functions.
6. **Check.** `python tus.py check <TU> --run 15`: build, stubgen, callcheck, layoutcheck (GCC + MSVC),
   smoke run with the scripted pad. Repeat until green. **Look at `work/shots/last.png`** (and the
   `shot_*.png` sequence) with the Read tool: **the picture is the test**. A drawing TU is `done` only
   when the screen shows what the game's own assets show (`tm2png.py` -> `work/ref/`); a wrong picture is
   `partial` with the difference in the notes; complete code nothing on screen shows yet is `verify`.
   When a run needs more than the boot, extend the smoke pad and say how far it gets in open-items.md.
7. **Record.** Facts -> architecture.md; traps -> hazards.md (symptom / cause / fix, dated); cross-TU
   questions and decisions -> open-items.md; better ways of working -> this file, reconstruction.md, the
   tools README. If `.claude/` writes are denied (autopilot), put the text in `--notes` after "For the
   references:", one item per file.
8. **Finish.** `python tus.py finish <TU> --status done|verify|partial|blocked --summary "..." --notes
   "<handoff for a reader with no context>" --coauthor "<the session's Co-Authored-By line>"`: builds
   (refuses red or a failed layoutcheck), records, refreshes, commits on the current branch (`git add
   -A`: check `git status` first; refuses `main`). Report in 3-5 lines and **stop**.

`blocked` means a decision is needed: say which in the notes and open-items.md. Never leave the tree
dirty or the build red.

## Starting sessions

The user starts each session (`/yamipan-port next`, a scheduled task whose prompt is
`tools/reverse/routine.md`, or `autopilot.py` in a terminal). A session never starts other sessions,
agents or scheduled tasks, and never edits `autopilot.py` or the routine. Within a session, run the
protocol without asking at each step; pause only for decisions that are the user's (restructuring the
tree, non-trivial platform changes, destructive git) -- when no answer can come, decide, record the
doubt in open-items.md, finish. Pushing finished commits is not approved for YamiPan yet (open-items.md).
An empty queue means re-assess, not "follow the frontier": the frontier counts call sites from written
code that may never run (in ReiPan it led seven sessions into effects nobody could see); refill the
queue from "Next up" in the order a smoke run reaches the stubs. Porting runs at effort `xhigh` (this
frontmatter; the user's rule: automated runs at xhigh or above). Keep that line.

## The user's rules (from the earlier ports; open-items.md "Decisions" has the dates)

- **The picture is the test.** Logs, stub hits and callcheck show the code ran, not that it is right.
- **Drawing never goes through the emulated GS.** Keep the game's draw decisions (what, where, colour,
  blend, order, textures), replace its output: the packet-writing step calls a native host draw module
  per subsystem under `src/yamipan/rendering/`, batched, layers in the game's order, textures on the GPU
  keyed by their owner record (RosePan architecture.md "PC platform layer").
- **Any aspect ratio**: from one renderer-owned source, never a fixed 4:3 / 640x448 in host draw code.
- **Methods, not free functions**: a function taking the object in a0 is a member.
- **Automated work at xhigh or above; sessions never start sessions.**

Naming exists to make reconstruction possible; it is not the goal. Name what the slice needs, then
write code; callees not needed yet become stubs.

## Naming conventions (Ghidra)

- Provenance tags on every name: `game-symbol` (the ELF's own symbol: exact, never renamed),
  `lib-match` / `lib-match-low` (libmatch.py), `lib-context` (library code named by reading),
  `game-inferred` (game code named from its code), `<sister>-match` / `<sister>-context` when names come
  from a sister build. `data/context_names.json` is the ledger with evidence; `data/overrides.json`
  lists replaced matches.
- Style: the game's own, as its symbols and strings show (RoR: `Class::lowerCamel`; FF: PascalCase with
  module prefix). Library functions their ABI names. No whitespace (`operator_new`); overloads carry
  their parameters. A name states what the code does; uncertainty goes in `why`. Assert expressions name
  fields.

## Keeping this skill alive

This file and its references are the project's memory across sessions; updating them is part of
finishing any session:

- **Generated** (`status.md`, `yamipan_functions.txt`): never hand-edit; `refresh.py` regenerates them.
- **Per-TU state and handoff** -> `tus.json` via `finish --notes` and `define --why`.
- **Facts** -> architecture.md with the address; replace what they supersede.
- **Guesses and cross-TU questions** -> open-items.md, resolved there.
- **Anything that burned time** -> hazards.md (Ghidra / MCP ones -> ghidra.md).
- **A better way of working** -> this file, reconstruction.md or the tools README; an instruction found
  wrong is fixed in the same commit.
- **Automation**: the same manual steps twice -> a script in `tools/reverse/` (Ghidra through
  `ghidra_mcp.py` / `yamipan.py`), in the README and here. Each TU should take less hand work than the last.
- **Lessons for every port** (Ghidra, the PS2 SDK, the platform layer) also belong in the sibling skill
  that owns the code they touch; say so in the report so the user can carry them over.
- Keep this file under ~250 lines; move detail into references.
